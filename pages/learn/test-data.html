Test Data & Environments

Most "flaky tests" are not flaky tests. They are two runs fighting over the same row, or a fixture that was true last Tuesday.

Why this page exists. Everything else on this site teaches you to write a test. This is about the ground it stands on. Data and environment problems are the most common cause of the flakiness the automation track tells you to eliminate, and almost nobody teaches them — which is also why "how do you manage test data?" separates candidates so cleanly in interviews.

Four ways to get test data, and what each costs

ApproachGoodThe cost you pay later
Static fixtures
A seeded database, a JSON file		 Fast, deterministic, readable. Everyone knows what user 7 is. Goes stale. Tests start depending on "the third row", and every test shares one mutable world.
Created per test
The test makes what it needs, usually via API		 Independent, parallel-safe, self-documenting. Usually the right default. Slower, needs a creation path, and leaks records unless you clean up.
Generated
Faker, factories, property-based		 Cheap volume, and randomness finds edge cases you would not have written. Non-deterministic failures. Seed your generator and log the seed, or a failure is unreproducible.
Copied from production
A restored or subsetted dump		 Realistic shape, realistic volume, realistic mess. Real people's data in a lower environment. See below — this is the one that becomes a legal problem.

Real suites mix them: seeded reference data that rarely changes (countries, product types, roles), created-per-test data for anything the test mutates. The failure pattern to recognise is a suite that used only the first approach and has quietly become a suite where every test depends on every other.

Why parallel runs collide

Two workers run at once. Both use qa@test.example. One signs in, the other changes that account's email mid-flow, and the first fails with something that looks nothing like the real cause.

The three collisions worth recognising by sight:

  1. Shared account. Two tests using the same login. The symptom is a test that passes alone and fails in the suite — the single most useful diagnostic signal there is.
  2. Shared unique value. Two tests both registering new@test.example. The second gets "already exists" and fails on a validation message that is completely correct.
  3. Order dependence. Test A creates what test B asserts on. Green for months, then the runner shards differently or someone adds a .only, and B fails alone.
The diagnostic that costs nothing: run the failing test by itself. Passes alone, fails in the suite means shared state, and you can stop reading the test's own code. Fails both ways means the test or the product is wrong. Two minutes of triage that decides which day you are about to have.

Making a test independent

The rule is one sentence: a test creates what it needs, asserts, and leaves nothing behind that another test can see. Everything below is a way of keeping it. 

// Colliding: every worker fights over one account.
const USER = 'qa@test.example';

// Independent: unique per test, and traceable back to the run that made it.
function uniqueEmail(label) {
  return `qa-${label}-${process.env.RUN_ID}-${crypto.randomUUID()}@test.example`;
}

test('a new account can be created', async ({ page, request }) => {
  const email = uniqueEmail('signup');
  // Created through the API: fast, and it is not what this test is verifying.
  await request.post('/api/users', { data: { email, plan: 'free' } });
  // ... exercise the UI, assert
});

Four habits that follow from it:

  • Set up through the API, assert through the UI. Creating a user by driving the signup form ten times makes ten tests that all fail when signup breaks. Only one of them was about signup.
  • Never reuse a unique field. Emails, usernames, order references, SKUs. A timestamp is not enough at speed — two workers can hit the same millisecond. A UUID is.
  • Clean up, but do not depend on cleanup. A test that only passes when the previous run cleaned up correctly has just reintroduced order dependence through the back door.
  • Tag what you create. A run id in the record means you can find and purge your own leftovers, and it tells you which run left the mess.

Where cleanup belongs is a genuine trade-off, and saying so is a good interview answer: after each test is tidiest but slowest and can hide the state you needed to debug; a scheduled purge is cheaper but leaves a dirty environment between runs.

Environments, and why shared ones lie

EnvironmentWhat it is forWhat it will not tell you
LocalFast feedback while writing.Anything about integration, scale, or config.
CI / ephemeralThe suite, on a clean environment built per run.Real data volume, real third parties.
StagingProduction-like config and integrations.Production data volume — and staging drifts unless it is rebuilt.
ProductionThe truth. Smoke tests and monitoring belong here.Nothing — but a destructive test here is a career event.

A shared staging environment is where suites go to become unreliable. Someone deploys mid-run; someone else is manually testing the same records; a third-party sandbox is rate-limiting all of you. The failures are real failures — of the environment, not the product — and a suite that cries wolf weekly stops being read.

The strong answer to "how would you fix our flaky pipeline" starts with an ephemeral environment per run, not with retries. Retries are the thing you add after you know what is failing, and the thing that hides it if you add them first.

Config is test data too. Feature flags, currency, locale, timezone, the seeded admin's permissions. A test that passes in CI and fails in staging is very often a flag that is on in one and off in the other — and pinning the flag inside the test is what makes it answerable.

Production data is a liability

Restoring a production dump into staging is the fastest way to get realistic data and it copies real people into an environment with weaker access control, wider access, and probably no audit trail. Under GDPR that is processing personal data for a new purpose, and testing is not a lawful basis on its own.

  • Mask or synthesise before it lands. Not after — a copy that arrives unmasked has already been disclosed to everyone with staging access.
  • Masking must be consistent. The same customer has to map to the same fake identity across every table, or the referential integrity you copied the data for is gone.
  • Beware the leftovers. Real email addresses in a test database get sent real email by an integration nobody remembered. This is a well-worn way to email thousands of customers by accident.
  • Subset, do not clone. A representative slice gives most of the realism at a fraction of the risk and restore time.

Being the person who asks "is this masked?" before a restore is cheap and it is remembered. It is also a question that reads as senior in an interview, because it shows you have thought past making the test pass.

What interviewers ask

  • "How do you manage test data?" Name the trade-off rather than a tool: seeded reference data that does not change, created-per-test for anything mutated, unique values on every unique field. Then say how you clean up.
  • "A test passes locally and fails in CI. What now?" Run it alone. Passing alone and failing in the suite points at shared state; failing both ways points at environment or config. Say the diagnostic before you say the cause.
  • "How do you make tests run in parallel safely?" No shared mutable data, unique values per test, setup through the API, and no assumption about ordering. Parallel safety is a data-design problem before it is a runner setting.
  • "Would you test against production?" Read-only smoke tests and synthetic monitoring, yes — with clearly marked synthetic accounts and no destructive actions. It is a real practice, not a trick question, and the answer is about blast radius.
  • "Can we just copy production data down?" Not unmasked. This is the one where a candidate who says "yes, that's easiest" loses the room.
