What manual testing actually is

Manual testing is a human executing the software with the intent to find defects — not just "clicking around." Done well, it's disciplined, hypothesis-driven, and produces a paper trail that survives handoff.

Two flavors that get conflated:

  • Scripted testing — pre-written test cases with defined steps, inputs, and expected results. Deterministic. Suited for regression suites, acceptance criteria verification, and anywhere reproducibility matters.
  • Exploratory testing — simultaneous learning, test design, and execution. Discovery-driven. Suited for new features, ambiguous requirements, and finding what scripted tests missed.

You do both. The mix depends on the product's maturity, regulatory constraints, and how quickly requirements change.

Test design techniques (the shortlist that matters)

Equivalence partitioning

Divide inputs into classes where the system should behave the same. Test one representative per class instead of every possible value.

Example: Age field 18–65 for adult ticket pricing → partitions are < 18, 18–65, > 65, and non-numeric. Four test cases instead of hundreds.

Boundary value analysis

Bugs cluster at boundaries. Test just below, at, and just above each boundary.

Example: Same age field → test 17, 18, 19 and 64, 65, 66. Pair this with equivalence partitioning; they're stronger together.

Decision tables

When behavior depends on combinations of conditions, enumerate them. Rows = conditions and actions; columns = rules. Any row with the same expected output for every combination is a candidate to collapse.

State transition testing

For features that have modes (draft → in review → published → archived). Diagram the states and transitions, test each legal transition, then explicitly test the illegal ones — those are where the interesting bugs live.

Pairwise / all-pairs

When many parameters interact, exhaustive testing is impossible. Pairwise generates a small set of tests that covers every pair of parameter values. Studies show most defects surface from single-parameter or pair-wise interactions, not higher-order combinations.

Error guessing

Experience talking. Empty inputs, whitespace-only, extremely long strings, Unicode, negative numbers, dates in leap years, timezone boundaries. Keep a checklist and add to it every time a bug bites you.

Exploratory testing — done professionally

Exploratory testing is not "no plan." It's session-based, charter-driven, and produces artifacts.

Structure a session:

  1. Charter — a one-sentence mission. "Explore the login flow with a focus on account lockout and rate limiting."
  2. Time-box — 60 or 90 minutes. Longer sessions lose sharpness.
  3. Notes — capture as you go: what you tested, what you observed, questions raised, bugs filed.
  4. Debrief — five minutes at the end to summarize findings, gaps, and what's worth automating.

Reference: Explore It! by Elisabeth Hendrickson is the canonical text. Keep charters, heuristics, and a running "cheat sheet of nasty inputs" in a notes file you carry between projects.

Bug reports that survive triage

A bad bug report burns cycles for you AND the developer. A good one gets fixed. The difference is a checklist:

  • Title — what + where + observed. "500 error on Save when Notes field > 500 chars (Profile page)".
  • Environment — browser, OS, build number/commit hash.
  • Steps to reproduce — numbered, minimal, deterministic. Someone else on a fresh machine should reproduce it blindly.
  • Expected result — separately from actual.
  • Actual result — what happened, including error messages verbatim.
  • Evidence — screenshot minimum; HAR file, console log, or screen recording for anything harder.
  • Severity (technical impact) and priority (business urgency) — separate judgments, each with a one-line reason.
  • Frequency — quantified. "Reproduces 5/5 times" beats "sometimes."
  • Regression? — if you can identify the last build it worked, name it. Saves hours in triage.
