Why automate at all

Automation is not about speed. It's about trust in a changing codebase. Every new feature risks breaking every old one. Manual regression at any real scale is impossibly expensive; automated regression is the only way to keep the safety net proportional to the code you own.

The economics are simple: the test costs once to write, then near-zero to run. If it runs 50 times over the life of the feature, the automation cost is 2% per run compared to a manual re-execution.

The test pyramid

Coined by Mike Cohn. A healthy suite is pyramid-shaped:

  • Base — many unit tests. Fast (ms), cheap, deterministic, isolated. Written alongside code by developers. Runs on every save.
  • Middle — integration / service / API tests. Slower (10s ms – seconds), more realistic. Verifies components talking to each other.
  • Top — end-to-end / UI tests. Slow (seconds – minutes), brittle, expensive to maintain. Cover the critical user journeys only.

The anti-pattern is the ice cream cone — most tests at the UI level, few at the unit level. Slow feedback, high maintenance, developers avoid running the suite locally.

Rule of thumb: if a lower level of the pyramid can prove the same behavior, prove it there.

What NOT to automate

  • Features still in churn. Cost of maintaining the test exceeds the cost of running it manually. Wait until the design stabilizes.
  • Exploratory testing. The value is human judgment. Automation removes exactly what makes it work.
  • Subjective checks. "Does this feel laggy?" "Is the copy on-brand?" — humans, not scripts.
  • One-off tests that will not run again.
  • Environments you can't control — real payment gateways, live third-party APIs without sandboxes.

Automate the boring, repetitive, high-value regressions. Keep humans for the interesting parts.

The Page Object Model

Wrap each page (or major component) in a class exposing element locators and high-level actions. Tests become readable and maintenance concentrates in one place.

// LoginPage.js
class LoginPage {
  constructor(page) {
    this.page = page;
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Password');
    this.submit = page.getByRole('button', { name: 'Sign in' });
    this.error = page.getByRole('alert');
  }
  async login(email, pw) {
    await this.email.fill(email);
    await this.password.fill(pw);
    await this.submit.click();
  }
}

// login.spec.js
test('bad password shows error', async ({ page }) => {
  const login = new LoginPage(page);
  await page.goto('/login');
  await login.login('u@x.com', 'wrong');
  await expect(login.error).toHaveText('Invalid credentials');
});

When the UI changes, you update one file. Tests stay readable.

Flaky tests — real causes and real fixes

Flake is not "the test framework is unreliable." Flake is almost always a real bug in either the test or the app. Do NOT default to retry.

Root causes and fixes:

  • Timing / no wait for state. Fix with an explicit wait for the specific condition (element visible, network idle, text present) — never sleep(3).
  • Test order dependency. Tests leak state between each other. Fix with fresh fixtures per test — reset DB, clear storage, delete created users.
  • Non-deterministic data. Timestamps, random IDs, current-date logic. Fix by mocking the clock or seeding random.
  • External dependencies. Third-party API returned different data. Fix with mocks or a stable stub.
  • Animation / debounce. Click landed mid-animation. Fix by waiting for a stable signal (an ARIA attribute, a class change, network idle).

Only quarantine + retry as a temporary measure with an owner and a due date. Never permanent.

CI integration

Tests you don't run don't protect you. Automated tests must run:

  • On every pull request (block merge if red).
  • On every merge to main (catches integration issues from concurrent PRs).
  • On a schedule against production-like environments (catches slow drift).

Guardrails for a CI suite:

  • Fail fast. Kill the run at the first failure if debugging, run to completion if reporting.
  • Parallelize. Shard the suite across workers; keep total wall time under ~10 minutes.
  • Track flake rate. Any test with > 1% flake gets fixed or quarantined that week.
  • Artifacts on failure. Screenshot, video, trace, browser console log, network log. Debugging without them is guessing.
