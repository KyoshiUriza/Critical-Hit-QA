Where to test, and why those widths

Testing "on mobile" is not a test plan. Pick widths for a reason, and be able to say what the reason was:

WidthWhy this one
320pxThe floor WCAG 1.4.10 Reflow is written against. If it works here it works everywhere.
375pxThe most common real phone width for years running.
390–430pxCurrent large phones. Often where a layout starts fitting and stops being tested.
768pxTablet portrait, and the classic breakpoint boundary — test at it and one pixel either side.
1280px+Desktop, where it was built and where it already works.

Two habits that separate a real responsive pass from a glance:

  • Test the boundary, not the middle. A breakpoint at 768px means 767 and 768 are different code paths. Bugs cluster on boundaries in layout for exactly the reason they do in input validation, and it is the same equivalence-partitioning skill.
  • Test both orientations at every width. Landscape phone is short, not wide — 375×667 becomes 667×375, and anything sized against the viewport's height suddenly has a third of the room. This is the least-tested state on the web.
Zoom is the same test. A user at 400% zoom on a 1280px desktop gets a 320px-equivalent viewport. That is not an edge case, it is WCAG 1.4.4 and 1.4.10, and it means your narrow-width findings apply to desktop users with low vision too. Say that in the bug report and the priority changes.

The five defects worth knowing by name

  1. Two-dimensional scrolling (reflow). The page scrolls sideways as well as down. Almost always one fixed-width child — a table, an image, a min-width nobody revisited. WCAG 1.4.10.
  2. A control that is present but unreachable. Clipped by an overflow, pushed outside a non-wrapping row, or covered by a sticky element. Check the DOM before you write "the button is missing" — missing and hidden get fixed by different people.
  3. Tap targets too small. WCAG 2.2 2.5.8 asks for 24×24 CSS pixels at Level AA; Apple's guidance says 44pt and Google's says 48dp. Measure the hit box, not the icon — a 16px glyph inside a 44px button is correct.
  4. Chrome eating the viewport. A sticky header, a cookie bar and a sticky footer that are each reasonable and together leave a band of content. Worst in landscape. Express it as a percentage of viewport height and the argument makes itself.
  5. State lost on rotation. Type into a form, rotate, and find it empty. The classic, and the one nobody tests. On a real device the same symptom can also come from the keyboard opening or the OS restoring a backgrounded app — worth distinguishing, because the fix differs.

Emulator, simulator, real device — and what each one lies about

ToolGood forWill not tell you
DevTools device mode Layout, breakpoints, reflow, tap-target measurement. Free and instant. Real touch behaviour, real performance, the on-screen keyboard, browser chrome that grows and shrinks as you scroll.
Simulator / emulator OS-level behaviour, real Safari or Chrome engine, permission dialogs. Performance on a cheap device, battery, real network, camera and sensors.
Real device The truth. Nothing — but you will only ever have two or three of them.

The practical answer to "how do you cover mobile" is a pyramid: nearly everything in device mode because it is free, the risky flows on a simulator, and the money paths on the one or two real devices your analytics say your users actually hold. Naming that trade-off is a better interview answer than naming a paid device cloud.

Measuring instead of squinting

"It looks cramped" gets closed as won't-fix. A number does not. These run in the DevTools console on any page: 

// Is the page scrolling in two directions?
document.documentElement.scrollWidth > document.documentElement.clientWidth

// What is causing it? Anything sticking out past the right edge.
[...document.querySelectorAll('*')]
  .filter(el => el.getBoundingClientRect().right > document.documentElement.clientWidth)
  .slice(0, 10)

// Which tap targets are under the 24x24 AA minimum?
[...document.querySelectorAll('a, button, input, select, [role="button"]')]
  .map(el => ({ el, r: el.getBoundingClientRect() }))
  .filter(({ r }) => r.width < 24 || r.height < 24)

// How much of the screen is header?
document.querySelector('header').getBoundingClientRect().height / window.innerHeight

Paste these into a bug report with their output. A finding that arrives with the selector of the offending element and its measured width is a finding a developer can act on without reproducing anything.

Automating it

Playwright emulates devices as a first-class concept, so responsive checks are ordinary tests rather than a separate discipline: 

const { devices } = require('@playwright/test');

// A whole project running the suite as a phone.
projects: [
  { name: 'phone', use: { ...devices['iPhone 13'] } },
]

// Or per-test, which is usually what you want for a layout assertion.
test('no horizontal scroll at the reflow floor', async ({ page }) => {
  await page.setViewportSize({ width: 320, height: 640 });
  await page.goto('/checkout');
  const overflows = await page.evaluate(() =>
    document.documentElement.scrollWidth > document.documentElement.clientWidth
  );
  expect(overflows, 'content requires 2D scrolling — WCAG 1.4.10').toBe(false);
});

Two things to say about this in an interview:

  • Assert measurements, not screenshots. A visual snapshot fails on a font rendering difference and tells you nothing about why. scrollWidth > clientWidth fails only when the defect is real, and the failure message can name the standard.
  • Emulation is not a device. A Playwright device descriptor sets viewport, user agent, device scale factor and touch support. It does not run WebKit's mobile engine on iOS hardware. Knowing what your automation does not cover is the point.

What interviewers ask

  • "How do you decide which devices to test on?" From analytics, not from a catalogue. Cover the widths your users actually have, plus 320px because it is the standard's floor.
  • "What's the difference between responsive and adaptive?" Responsive is one fluid layout that reflows continuously; adaptive serves distinct layouts at fixed breakpoints. Most real sites are a mixture, which is why boundary testing matters.
  • "How would you test a form on mobile?" Correct keyboard type per field, no zoom-on-focus, the keyboard not covering the submit button, autofill, and rotation mid-entry. The last one finds bugs almost every time.
  • "Is emulation enough?" For layout, largely yes. For touch, performance, and anything OS-mediated, no — and say which of your flows justify a real device.
  • "How is this different from accessibility testing?" It substantially overlaps. Reflow, tap-target size and zoom are WCAG criteria. Someone who can point that out has understood both.

Practice — earn Star-Dust

  1. Work the Responsive Lab through every preset, in both orientations. Five defects are seeded; three of them only exist below 480px and one only appears when you rotate.
  2. Measure each finding with the console snippets above rather than describing it.
  3. Repeat the pass in DevTools device mode on the same page — the frame and real emulation disagree about some things, and noticing which is the lesson.
  4. Write the worst one up in the Bug Report Builder, with the measurement and the criterion.
  5. Cross-check against the Accessibility track — three of the five are also WCAG failures.
