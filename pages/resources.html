HTTP status code cheat sheet

Full list on MDN →
2xx — Success
  • 200 OK — generic success
  • 201 Created — resource created
  • 202 Accepted — async work started
  • 204 No Content — success, no body
3xx — Redirection
  • 301 Moved Permanently
  • 302 Found (temp redirect)
  • 304 Not Modified (cache)
4xx — Client errors
  • 400 Bad Request
  • 401 Unauthorized (not authenticated)
  • 403 Forbidden (authenticated but no access)
  • 404 Not Found
  • 409 Conflict (e.g., duplicate)
  • 422 Unprocessable Entity (validation)
  • 429 Too Many Requests (rate limit)
5xx — Server errors
  • 500 Internal Server Error
  • 502 Bad Gateway
  • 503 Service Unavailable
  • 504 Gateway Timeout

When a developer disputes what a code means, the argument ends at RFC 9110 §15, which defines them normatively. The 401-vs-403 distinction in particular is worth being able to cite.

Test design techniques cheat sheet

  • Equivalence Partitioning — divide inputs into classes, test one per class.
  • Boundary Value Analysis — test at, just below, and just above each boundary.
  • Decision Table — enumerate combinations of conditions and expected outcomes.
  • State Transition — enumerate states and valid/invalid transitions.
  • Pairwise / All-pairs — cover all pairs of parameter values with fewer tests than exhaustive. pairwise.org explains the maths and lists generator tools.
  • Error Guessing — apply experience/intuition to guess where defects hide.
  • Exploratory (charter-based) — time-boxed exploration with an explicit mission. James Bach's Heuristic Test Strategy Model is the standard framework for structuring one.
  • Use case / scenario — walk through end-to-end user journeys.

Precise definitions for all of these live in the ISTQB Glossary. Worth checking before an interview — interviewers tend to use the ISTQB wording even when they have never sat the exam.

Testing types quick reference

By level
  • Unit
  • Component / Integration
  • System
  • User Acceptance (UAT)
By purpose
  • Smoke — broad, shallow
  • Sanity — narrow, deep
  • Regression — verify nothing broke
  • Retest / Confirmation — verify a fix
By approach
  • Manual vs. Automated
  • Static (reviews) vs. Dynamic (execution)
  • Black-box, White-box, Grey-box
Non-functional
  • Performance (load, stress, spike, soak)
  • Security — OWASP Top 10
  • Accessibility — WCAG 2.1 AA
  • Usability
  • Compatibility (browsers, devices, OS)
  • Localization / Internationalization

Two of these have tooling that makes them testable rather than theoretical. The WCAG Quick Reference filters the spec down to the success criteria that apply to what you are looking at, and axe catches a meaningful slice of accessibility defects automatically — enough to be worth running, not enough to stop there.

Being able to name a specific OWASP category, rather than saying "I'd test for security", is a noticeable interview differentiator.

Glossary

Full ISTQB glossary →
Test case
A set of preconditions, inputs, steps, and expected results that verifies a specific requirement.
Test suite
A collection of related test cases.
Test plan
Document describing scope, approach, resources, and schedule of testing.
Traceability matrix
Maps requirements to test cases (and defects) to prove coverage.
DoD / DoR
Definition of Done / Ready — team agreements on when a story is complete or ready to work on.
Flaky test
A test that intermittently passes and fails without code changes. Root causes: timing, shared state, external dependencies.
Shift-left / Shift-right
Testing earlier in the SDLC (shift-left) or in production (shift-right, e.g., canary, feature flags, chaos).
Mock vs. Stub vs. Fake
Stub returns canned answers; mock verifies interactions were made; fake is a working lightweight implementation (e.g., in-memory DB). These three get used interchangeably in the wild; Martin Fowler's Test Double is the reference people actually mean when they claim there is a difference.
SUT
System Under Test.
Test double
Umbrella term for anything that replaces a real dependency (mocks, stubs, fakes, spies, dummies).
Page Object Model
A pattern that puts page structure behind a named API so a UI change breaks one file instead of forty. Fowler's original write-up is short and is what interviewers are checking you have read.
Test pyramid
Many fast unit tests, fewer integration tests, fewest end-to-end tests. The Practical Test Pyramid covers both the shape and the common objections to it.

Suggested reading

Start with the free one. The ISTQB syllabus gives you the vocabulary interviewers use, and costs nothing but an afternoon.

  • ISTQB Foundation Level syllabus — free, ~150 pages. The standard vocabulary base, and the source most interview questions are quietly drawn from. Free PDF
  • Lessons Learned in Software Testing — Kaner, Bach, Pettichord. 293 short lessons. The one to read if you only read one — it is skimmable and quotable in interviews.
  • Explore It! — Elisabeth Hendrickson. Turns exploratory testing from "clicking around" into a method you can describe on demand. Directly useful for the bug hunts on this site.
  • Agile Testing and More Agile Testing — Crispin & Gregory. Where the testing quadrants come from. Read the first before the second.
  • xUnit Test Patterns — Gerard Meszaros. A reference, not a read-through. This is where the precise mock/stub/fake definitions live.
  • Continuous Delivery — Humble & Farley. Explains where testing sits in a deployment pipeline. Useful once you are being asked about CI, not before.

Where to keep learning

Documentation and communities worth a bookmark rather than a one-off read.

Tool documentation
  • Playwright docs — genuinely well written; the locators and assertions pages are the two that matter most.
  • Selenium docs — still what a large share of job postings ask for.
  • MDN HTTP reference — for anything API testing touches.
Browser extensions
  • SelectorsHub — a DevTools panel that writes and verifies XPath, CSS, and Playwright locators as you type, and tells you when one is wrong instead of leaving you to find out in CI. It handles the two cases that usually defeat hand-written selectors: shadow DOM (including closed roots) and nested iframes. Free tier is enough; Chrome, Edge, Firefox, Opera, Brave.

One caution, because it is the same trap as self-healing locators: a generated selector is a starting point, not an answer. The Locator Lab exists to teach you to judge one — a tool that hands you div:nth-child(3) > span has solved "does it match" and not "will it still match".

Communities & writing
  • Ministry of Testing — the largest active testing community; the forum is a good place to ask beginner questions without being flamed.
  • Google Testing Blog — the archive on flaky tests and test sizing is worth mining.
  • martinfowler.com/testing — the source of most of the vocabulary the industry reuses.

Interview prep checklist

Each item links to where you can actually practise it, rather than just read about it.

  • Know the definitions: verification vs. validation, severity vs. priority, smoke vs. sanity. — Interview questions
  • Explain the SDLC / STLC and where you fit in Scrum. — Learn tracks
  • Design a test plan for a familiar feature end-to-end (login is a classic). — Login practice app
  • Walk through boundary and equivalence with a concrete example. — Fundamentals quiz
  • Know when NOT to automate. — Automation track
  • Explain the test pyramid and page object model.
  • Understand HTTP basics and how you'd test a REST endpoint. — MDN HTTP
  • Be able to write a locator that will not go flaky. — Locator Lab
  • Prepare 2–3 STAR stories: critical bug found, disagreement with dev, process improvement. — a real find from a bug hunt works as the first one.
  • Have a written bug report you can show. — Your portfolio
  • Have questions ready for them: quality culture, ratio of manual to automation, deployment cadence.
