Why a tester needs SQL

A UI that shows "Saved" is a claim, not evidence. SQL is how you check the claim. Three situations come up constantly:

  • Verify a write. The form said success — did a row actually appear, with the right values, in the right table?
  • Set up state. You need a user with 47 orders and an expired subscription. Clicking through the UI to build that takes twenty minutes; a seed script takes one.
  • Explain a defect. "The dashboard total is wrong" becomes actionable when you can say the aggregate query returns 14 but the UI renders 12.

You are not expected to optimise queries. You are expected to read data confidently and not break the environment.

The six queries that cover most days

1. Verify a record

SELECT * FROM users WHERE email = 'qa@test.com';

Confirm the UI wrote to the database. Run it before the action too — knowing the row didn't already exist is half the evidence.

2. Check related data

SELECT o.id, o.total, o.status
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.email = 'qa@test.com';

Follow a record across tables after a workflow. Most "the data looks fine" bugs are actually a broken foreign key relationship.

3. Count and group

SELECT status, COUNT(*) AS total
FROM orders
GROUP BY status
ORDER BY total DESC;

Validate dashboard aggregates. If the UI says 12 Pending and this says 14, you have a filter bug — and you have the number to put in the report.

4. Find the newest row

SELECT * FROM logs
ORDER BY created_at DESC
LIMIT 10;

Pull the record your test just created. ORDER BY … DESC LIMIT n is the single most-used pattern in test verification.

5. Catch missing data

SELECT * FROM users WHERE last_login IS NULL;

NULL means "no value." It is not an empty string and it is not zero. Test both — see below.

6. Clean up test data

-- ALWAYS run the SELECT first.
SELECT * FROM users WHERE email LIKE '%@test.example%';

-- Only then, with the same WHERE clause:
DELETE FROM users WHERE email LIKE '%@test.example%';

The SELECT-first rule exists because DELETE has no undo. See the section below before you run this anywhere real.

Joins, without the diagram

Four joins matter. The difference is only ever "what happens to rows with no match on the other side."

JoinReturnsTest use
INNER JOINOnly rows matching in both tablesDefault. "Orders that have a valid user."
LEFT JOINAll left rows; NULLs where no matchFinding orphans — the highest-value join for a tester.
RIGHT JOINAll right rows; NULLs where no matchRare. Usually a LEFT JOIN written backwards.
FULL OUTER JOINEverything from both sidesReconciliation between two systems.

The orphan check — worth memorising, because it finds real data-integrity bugs:

-- Orders whose user no longer exists.
SELECT o.id, o.user_id
FROM orders o
LEFT JOIN users u ON o.user_id = u.id
WHERE u.id IS NULL;

If this returns rows, either a delete cascaded wrongly or one never cascaded at all. Both are bugs worth filing.

NULL is not empty string

This distinction produces real defects and comes up in interviews often enough to be worth over-learning.

-- These are three DIFFERENT states:
SELECT * FROM users WHERE nickname IS NULL;   -- never set
SELECT * FROM users WHERE nickname = '';      -- set, but empty
SELECT * FROM users WHERE nickname = ' ';     -- set to whitespace

Two consequences that catch people out:

  • nickname = NULL never matches anything. NULL is not equal to itself. You must use IS NULL.
  • COUNT(column) skips NULLs; COUNT(*) doesn't. A dashboard that undercounts is often exactly this.

The test-design takeaway: any nullable column has at least three cases to cover, not two.

Deleting test data without an incident

Every experienced tester has a story here, and the ones who don't have simply not run DELETE yet. Four rules:

  1. SELECT first, always. Run the exact WHERE clause as a SELECT and read the row count. If it surprises you, stop.
  2. Wrap it in a transaction where the engine supports it: 
    BEGIN;
DELETE FROM users WHERE email LIKE '%@test.example%';
-- check the reported row count, THEN:
COMMIT;   -- or ROLLBACK; if it looks wrong
  3. Never DELETE without a WHERE. It empties the table. Some clients have a safe-mode setting that blocks this — leave it on.
  4. Know which environment you're connected to. Colour-code your production connection in whatever client you use. The most expensive incidents in this category are a correct query run against the wrong database.

A note on LIKE '%test%': that pattern matches contest@real-customer.com. Prefer a reserved domain like @test.example — .example is reserved by RFC 2606 and can never belong to a real user.

What interviewers actually ask

  • "Write a query to find users who haven't logged in." Watch for the NULL trap — they want IS NULL, and often a follow-up about users who never had the column set versus users who logged out.
  • "How would you verify this feature end to end?" A strong answer includes checking the database, not just the UI.
  • "Second-highest salary." A classic. Know both approaches: 
    -- With a subquery
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- With a window function (preferred in modern engines)
SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;
  • "Find duplicates." GROUP BY … HAVING COUNT(*) > 1. The follow-up is usually "now delete them but keep one" — say out loud that you'd SELECT first.
  • "What's the difference between WHERE and HAVING?" WHERE filters rows before grouping; HAVING filters groups after.
