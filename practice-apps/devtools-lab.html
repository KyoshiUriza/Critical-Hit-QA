DevTools Lab

Four times the interface tells you one thing and the browser knows another. Go and get the evidence.

Why this exists. Hiring managers report rejecting candidates for failing elementary tasks — reading a console log, checking what a request returned, looking at what was actually stored. This site already covers running queries and calling an API. It did not cover reading the browser, which is the tool you will use every single day.

Everything here is real. The console entries are real console entries, the failed request is a real 404 in the Network tab, and the storage write is real localStorage. Nothing on this page is a mock-up of DevTools — a simulated panel would teach you the simulation.

Nothing fires until you press a button, so open the panel first and watch it happen. That is also the habit worth building: act, then read.

Answers are values you can only get from the panel. That is deliberate — a question you could answer from the page would be testing reading, not tooling.

The four panels, and when to reach for each

PanelAnswers the questionPut in the bug report
Console Did the code complain? The exact error text and the file:line it came from.
Network What did the server actually return? Method, URL, status, and how long it took. A HAR export if it is intermittent.
Application What was really stored, and where? The key name and its value — redacted if it contains anything sensitive.
Elements Is it missing, or just invisible? The element, and the computed style that hides or disables it.

One habit worth more than any of them: reproduce with the panel already open. Console and Network only record while they are watching, so a defect reproduced first and inspected second often leaves no evidence at all.
