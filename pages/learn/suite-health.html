Suite Health

How to tell whether your test suite is an asset or a liability — with worked examples from this site's own suite, which you can read.

Every example on this page is real and in the repository. This site is tested by a Playwright suite that runs on every push. Several of its tests exist because a specific defect shipped, and the comment above each one says which. That is unusual to be able to show a learner, so the file names below are worth opening: the tests directory.

Four numbers worth tracking

MetricWhy it mattersWhen to act
Wall-clock runtime The single biggest driver of whether people run the suite before pushing. A suite nobody runs locally finds things a day late. When it stops fitting in the gap people are willing to wait — for most teams, ten minutes.
Flake rate The percentage of runs that fail and then pass unchanged. This is the number that decides whether failures get read. Anything above a few percent. Past roughly one in ten, people start re-running by reflex and the suite has stopped working.
Time to diagnose a failure Rarely measured and enormously important. A red build that takes an hour to understand costs more than the bug did. When failure messages need someone to open the code to interpret. Assertion messages are the cheap fix.
Escaped defects Bugs found in production that the suite could plausibly have caught. The only metric that measures whether the suite does its job. Every one of them. Each is a specific, answerable question about a specific gap.

Notice what is absent: test count. A suite of 500 tests is not healthier than one of 200, and reporting the number as an achievement is how teams end up with hundreds of tests asserting the same happy path. Growth in test count is a cost as well as a benefit, and it should be justified the same way any other code is.

Flake rate, as a number

"The suite is a bit flaky" is not actionable. A percentage is: 

flake rate = runs that failed then passed with no code change
             ─────────────────────────────────────────────────
                              total runs

Playwright records this for you — a test that fails and passes on retry is reported as flaky, distinct from failed. If you are running with retries above zero, that number is already being produced on every run and is almost certainly being thrown away.

Retries hide the number they are meant to help you fix. Retrying a flaky test is a reasonable operational choice — it keeps a pipeline moving. Retrying it and not recording that it retried is how a suite gets to a 30% flake rate without anyone noticing. Configure retries if you need them, then track the flaky count as a metric with a target, or you have simply bought silence.

This site's own config sets retries: 1 on CI and zero locally. That is deliberate: locally a flaky test should fail loudly while you are the person who can fix it. The asymmetry is worth copying.

Why coverage percentage misleads

Line coverage measures which lines were executed, not which behaviors were verified. A test that calls every function and asserts nothing scores 100%. 

// 100% line coverage of applyDiscount. Zero behavior verified.
test('discount', async () => {
  await applyDiscount(basket, 'TRAIL10');
  expect(true).toBe(true);
});

What to say about coverage in an interview:

  • It is a floor, not a target. Low coverage reliably tells you something is untested. High coverage tells you almost nothing.
  • Uncovered lines are the useful output. The list of what was never executed is a genuine to-do; the percentage is a number for a slide.
  • A coverage target creates coverage-shaped tests. Mandate 80% and you will get assertion-free tests that reach 80%. This is Goodhart's law and it happens every time.
  • Mutation testing is the honest version. It changes the code and checks whether a test notices. Slow, and it measures the thing coverage pretends to.

Guards: tests that stop a claim from rotting

Most tests check the product. A guard checks that something you asserted elsewhere is still true — a number in the docs, a count on a page, a promise in a README. They cost almost nothing and they catch a class of defect that reviews never do.

This site's suite has several, and every one of them was written after the thing it guards had already drifted:

GuardWhat had gone wrong
catalog.spec.js The home page advertised 14 practice apps while shipping 16, and a card advertised 9 seeded defects in an app that had 8 — so learners were told to hunt for a bug that had been removed.
smoke.spec.js The sitewide sweep ran against a hand-written list of pages that had fallen five apps behind, including two shipped the same day. It now reads the filesystem.
labs.spec.js The Locator Lab grew to nine exercises and three pages still said six.
contrast.spec.js Color pairs were documented as passing WCAG with ratios that had never been computed. The test computes them.

The pattern in all four: a hand-maintained list drifted from the thing it described. The fix is never to update the list — it is to derive it from the source, so it cannot be wrong again. If you take one idea from this page into a real job, take that one.

A test per shipped defect

The cheapest high-value test you can write is one that reproduces a bug that reached users. It is already reproduced, its value is proven, and it never needs justifying.

The convention worth adopting: say why the test exists.

// The RPG chip must mount on EVERY page. Nine pages shipped without
// rpg.js, so the chip was absent there and the header's justify-between
// slid the nav to the right edge — the nav visibly jumped sideways as
// you navigated between chip and chip-less pages.
await expect(page.locator('.site-header .rpg-chip')).toBeVisible();

That comment is from this site's smoke suite, and it is doing real work. Two years from now someone will find this assertion inconvenient. The comment is the difference between deleting it and understanding what it was protecting. A test without one is a test that gets removed the first time it is in the way.

Where regression tests belong. Push each one to the lowest level that can catch it. A calculation error belongs in a unit test, not an end-to-end journey. The e2e suite should hold the journeys that only exist at that level — and staying disciplined about this is the main defense against the runtime metric at the top of this page.

What interviewers ask

  • "How do you know your tests are any good?" Escaped defects and flake rate, both as numbers over time. Test count and coverage percentage are the answers that get a follow-up you do not want.
  • "What's your flake rate?" If you can answer with a number you are already unusual. If you cannot, say how you would start measuring it — that is a good answer too.
  • "What do you do about a flaky test?" Quarantine it so it stops eroding trust, then fix or delete it on a deadline. A quarantine with no deadline is a graveyard.
  • "Our suite takes 45 minutes. What now?" Find out where the time goes before doing anything. Usually a handful of tests, or a setup path being driven through the UI once per test. Parallelism is a real answer but it is the second one.
  • "When would you delete a test?" When it tests something no longer true, duplicates a cheaper test, or has been failing for weeks and nobody looks. A suite people ignore is worse than a smaller one they trust.
