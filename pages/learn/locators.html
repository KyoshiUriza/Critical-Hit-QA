Locators & Flaky Tests

Locator choice is the single largest maintenance cost in UI automation — and the most common cause of tests that fail for reasons unrelated to the bug you were looking for.

The priority order

Work down this list and stop at the first one that fits. The order is not arbitrary — it runs from "describes what the user perceives" to "describes where the element happens to sit in the DOM today."

#LocatorUse whenWhy it's durable
1getByRoleAlmost alwaysMatches the accessibility tree. Changes only when the element's meaning changes — and it tests a11y as a side effect.
2getByLabelForm controlsLabels are user-visible copy. If it changes, a human decided it should.
3getByPlaceholderInputs with no labelWorkable, but a missing label is itself an a11y defect worth filing.
4getByTextStatic copyFine for fixed text. Never for text that carries state.
5getByTestIdNothing above fitsStable by contract — it exists only for tests, so nobody refactors it away by accident.
6CSSStructural targetingDepends entirely on which attributes you lean on. See the smells below.
7XPathGenuinely last resortPowerful, but the syntax invites absolute paths — the most brittle thing you can commit.

The one-line version: locate the element the way a user would describe it, not the way the DOM happens to be assembled.

Six locator smells

Each of these produces a test that passes in review and fails later — the expensive kind of failure, because nobody is watching when it breaks.

1. Build-generated class names

.css-1x2y3z, .sc-AbCdEf, .Button_root__3kd9f

CSS-in-JS and CSS Modules hash class names from file content. Change the stylesheet — or just upgrade the bundler — and every one of these changes. You will get a red suite from a deploy that touched no behaviour at all.

2. Framework-generated ids

#input-48213, #mui-4821, #:r7:

These are assigned per render. They differ between your machine and CI, and often between two runs on the same machine. This is the number one source of "it passes locally."

3. Positional selectors

:nth-child(3), .nth(2), tr[4]

Position is not identity. The failure mode here is the nastiest on the list: after a sort order changes or a row is inserted, the locator still matches something — just the wrong thing. The test keeps passing while asserting against the wrong record.

4. Absolute XPath

/html/body/div[2]/div[3]/main/div/form/button

This is what "Copy full XPath" in DevTools gives you. It encodes every ancestor. One new layout wrapper — a banner, an A/B test container, a theme provider — and every locator of this shape breaks simultaneously.

5. Stateful text

getByText('Cart (0)'), getByText('3 unread')

The text encodes application state, so the locator only matches in one state. Tests pass or fail depending on execution order — the definition of flaky.

6. Styling attributes

[style*="display: block"], .mt-4

Presentation changes for visual reasons that have nothing to do with what the element is.

Strict mode, and why it's a feature

When a Playwright locator resolves to more than one element, it throws rather than guessing:

Error: strict mode violation: locator('.row-delete') resolved to 3 elements

This reads like an obstacle the first time you hit it. It isn't. The alternative — silently acting on the first match, which is what older tools did — means your test clicks Delete on whichever invoice happens to be first. It passes. It deletes the wrong record.

Strict mode converts a silent wrong-element bug into a loud error. Fix it by narrowing, never by adding .first() reflexively — that just re-introduces the positional problem you were warned about.

Scoping: the technique that solves most of it

Most strict-mode violations are not "I need a more specific selector." They're "I need to say which region I mean." Chain from a stable ancestor:

Row-scoped action

// Brittle: which of the three Delete buttons?
await page.locator('.row-delete').nth(1).click();

// Durable: name the row, then the action inside it.
await page
  .getByRole('row', { name: /Invoice #1042/ })
  .getByRole('button', { name: 'Delete' })
  .click();
// Brittle: which of the three Delete buttons?
await page.locator('.row-delete').nth(1).click();

// Durable: name the row, then the action inside it.
await page
  .getByRole('row', { name: /Invoice #1042/ })
  .getByRole('button', { name: 'Delete' })
  .click();

The same shape solves duplicate buttons inside dialogs:

await page
  .getByRole('dialog')
  .getByRole('button', { name: 'Confirm' })
  .click();
await page
  .getByRole('dialog')
  .getByRole('button', { name: 'Confirm' })
  .click();

Two more scoping tools worth knowing:

// filter() — narrow a set by what it contains
await page.getByRole('listitem')
  .filter({ hasText: 'Overdue' })
  .getByRole('button', { name: 'Pay' })
  .click();

// and() — require several conditions at once
await page.getByRole('button')
  .and(page.getByTitle('Save draft'))
  .click();
// filter() — narrow a set by what it contains
await page.getByRole('listitem')
  .filter({ hasText: 'Overdue' })
  .getByRole('button', { name: 'Pay' })
  .click();

// and() — require several conditions at once
await page.getByRole('button')
  .and(page.getByTitle('Save draft'))
  .click();

Locators vs. waits — a related failure

A locator problem and a timing problem produce the same symptom: an intermittent failure. Telling them apart saves hours.

  • Locator problem — fails consistently on a given state, or matches the wrong element. Reproduces reliably once you know the state.
  • Timing problem — same locator, sometimes found, sometimes not. Usually correlates with machine load or network speed.

Playwright's auto-waiting removes most timing problems for you. Before acting, it waits until the element is attached, visible, stable (not animating), enabled, and able to receive events. So:

// Wrong: fixed sleeps are both slow AND still flaky.
await page.waitForTimeout(3000);
await page.locator('#save').click();

// Right: assert the condition you actually care about.
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
await page.getByRole('button', { name: 'Save' }).click();

// Also right: let auto-wait do it. click() already waits for actionability.
await page.getByRole('button', { name: 'Save' }).click();
// Wrong: fixed sleeps are both slow AND still flaky.
await page.waitForTimeout(3000);
await page.locator('#save').click();

// Right: assert the condition you actually care about.
await expect(page.getByRole('button', { name: 'Save' })).toBeEnabled();
await page.getByRole('button', { name: 'Save' }).click();

// Also right: let auto-wait do it. click() already waits for actionability.
await page.getByRole('button', { name: 'Save' }).click();

If you ever reach for { force: true }, stop. That flag skips the actionability checks — it doesn't fix the reason the element wasn't actionable. Nine times in ten it's covered by something, disabled, or mid-animation, and forcing the click hides a real bug.

Common Playwright errors, decoded

Most of these trace back to a locator or a wait. See the full reference on the Playwright Errors page.

ErrorUsual causeFix
strict mode violationLocator matched several elementsScope to an ancestor or use filter() — not .first()

element is not visibleHidden, zero-size, or coveredWait for the state that reveals it; scrollIntoViewIfNeeded() if genuinely off-screen
element is not attached to the DOMRe-rendered between locate and actUse a Locator (lazy, re-resolves) rather than a captured handle
