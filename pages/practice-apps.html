How to use these

  1. Open an app and interact with it as a user.
  2. Write test cases covering positive, negative, boundary, security, and accessibility scenarios (see the Test Case Builder).
  3. Automate them against the same app — locators use data-testid so your selectors stay stable. See the Automation Lab.
  4. Read the "Try to find..." hints to discover intentional bugs and edge cases.
  5. Try the Buggy variant of each app — it works like the clean version but has intentional defects. See how many you can catalog, then score yourself in Bug Bounty — that is where the answer key lives.

How to work a buggy app — the professional way

  1. Read the spec. The panel next to each app tells you what SHOULD happen. That's your oracle.
  2. Charter your session. Time-box (20-30 min), pick a focus (validation? calculations? security?), take notes as you go.
  3. Try to break it. Boundary values, invalid types, empty submits, whitespace, unicode, huge inputs, rapid clicks, refresh mid-flow, back button.
  4. Log each defect properly. Title (what + where + observed), steps to reproduce, expected vs. actual, severity/priority, evidence. Use the Test Case Builder — its format works for bug reports too.
  5. Open the answer key in Bug Bounty ONLY after you have drafted your list. Then compare: what did you catch? What did you miss? What did you find that isn't on the key (bonus points)?

Test-case starter template

For every practice app, cover at least:

  • Positive: happy path with valid input.
  • Negative: invalid input, missing fields, wrong types.
  • Boundary: min-1, min, max, max+1 for every constrained input.
  • Security: XSS payload in each text field, SQL-injection-shaped strings, extremely long input.
  • UX / A11y: keyboard-only navigation, screen reader labels, focus order, error visibility.
  • State: refresh page, back button, open in two tabs, offline.
