Playwright deep dive

Microsoft-backed, released 2020, written by the team that previously built Puppeteer at Google. Designed from the start around the pain points a decade of Selenium exposed.

Install and run

npm init playwright@latest
npx playwright test
npx playwright test --ui         # interactive mode
npx playwright show-trace tr.zip # inspect a failed run

The core primitives

  • Browser — a browser process (chromium, firefox, webkit).
  • Context — an isolated browser session, its own cookies and storage. Each test gets a fresh one by default.
  • Page — a tab within a context. You do most of your work through this.
  • Locator — a lazy, re-resolving reference to an element. Never a "stale element" exception.

Recommended locators (in order)

page.getByRole('button', { name: 'Sign in' })   // best — semantic
page.getByLabel('Email')
page.getByPlaceholder('you@example.com')
page.getByText('Welcome back')
page.getByTestId('login-submit')                 // stable data-testid
page.locator('css=.some-class')                  // last resort

Auto-wait — what actually happens

When you call await locator.click(), Playwright waits until the element is:

  • Attached to the DOM
  • Visible (not display:none, not zero-size)
  • Stable (not in transit due to animation)
  • Enabled
  • Receiving events (not covered by another element)

All within a default 30-second timeout. This eliminates a huge class of flake without a single explicit wait.

Trace viewer — the killer feature

Add trace: 'on-first-retry' to your Playwright config. On failure, run npx playwright show-trace and get a full timeline: DOM snapshot before/after every action, network calls, console logs, screenshots, source. Diagnosing a flaky failure goes from hours to minutes.

Selenium deep dive

The granddaddy. WebDriver became a W3C standard in 2018 largely because of Selenium's ubiquity. Selenium 4+ ships true W3C WebDriver, relative locators, and a modernized Grid.

Install (Python)

pip install selenium
# WebDriver Manager handles the driver binary in Selenium 4+
python -c "from selenium import webdriver; d = webdriver.Chrome(); d.get('https://example.com'); d.quit()"

The core primitives

  • WebDriver — the browser session.
  • WebElement — a reference to a DOM element. Stale-element-reference exceptions happen when the DOM re-renders.
  • By — locator strategies: By.ID, By.CSS_SELECTOR, By.XPATH, and (Selenium 4+) relative locators like above, below, near.
  • WebDriverWait + ExpectedConditions — the explicit-wait mechanism.

Explicit wait pattern

from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC
from selenium.webdriver.common.by import By

el = WebDriverWait(driver, 10).until(
    EC.element_to_be_clickable((By.CSS_SELECTOR, '[data-testid="login-submit"]'))
)
el.click()

Selenium does not auto-wait. If you skip explicit waits you get flake. Never sleep.

Selenium Grid

For scale: run tests distributed across many browsers/OSes. Grid 4 supports Docker containers per session, native browser sandboxing, and cloud providers like Sauce Labs, BrowserStack, LambdaTest slot in seamlessly.

Where Selenium still wins

  • Language coverage — need Java, Ruby, C#, Kotlin? Selenium has first-class bindings; Playwright doesn't for all of them.
  • Any browser with a WebDriver — including embedded browsers, older builds, exotic platforms.
  • Massive existing test suites — migrating a decade of Selenium tests to Playwright is a project, not a decision.
  • Corporate policy or standards mandating W3C WebDriver.

Locator strategies that survive UI change

Locator brittleness is the single largest maintenance cost in UI automation. Rank your locator choices from best to worst:

  1. Semantic queries. getByRole('button', { name: 'Sign in' }) — what a screen reader sees. Cheapest to maintain; also tests accessibility as a side effect.
  2. Test-specific attributes. data-testid="login-submit". Add these deliberately to the app; they survive style refactors.
  3. Stable IDs. Not auto-generated ones like id="mui-generated-42".
  4. Text content. Fine if the text is stable and unique enough.
  5. CSS class of a specific-looking class. Only if you own the class name and won't refactor styles.
  6. Absolute XPath. Almost always wrong. Breaks the moment a wrapper div gets added.
  7. Positional / nth-child. Guaranteed to break within the year.

The practice apps on this site all expose data-testid attributes for exactly this reason.

Waits, done right

  • Never sleep. A fixed sleep(2) is both too slow (when things are fast) and still flaky (when things are slow). Zero justifications.
  • Wait for a specific condition — element visible, network request done, ARIA attribute changed, text present.
  • Framework-level auto-wait > manual wait where available (Playwright). Skip the ceremony.
  • Waiting for network idle is a heuristic — brittle if your app polls. Prefer waiting for the specific request whose result matters.
  • Long timeouts hide bugs. A 60-second wait that always succeeds in 200ms is fine. One that regularly takes 30 seconds is telling you something.

Choosing between them (2026 view)

  • Greenfield project, JS/TS-native team, modern web app → Playwright. Lower ceremony, faster feedback, trace viewer alone is worth it.
  • Team is Java/Python/C# by default and you want first-class language support → Playwright works in all of these too. Playwright is the safer pick for greenfield across the board today.
  • Existing large Selenium investment → don't rewrite. Migrate incrementally by writing new tests in Playwright and letting the Selenium suite age out.
  • Need Ruby / Kotlin / a niche browser / an on-prem Grid → Selenium is still the answer.
  • Team-of-one or hobby project → Playwright. Setup is a single command.

Playwright is the safer default pick for greenfield projects in 2026. Selenium remains the right call when your constraints — language, browser, existing suite, standard — require it.

Practice — earn Star-Dust

  1. Take the Automation quiz — aim ≥ 85%.
  2. Install Playwright locally. Serve this project (python -m http.server 8080) and run the login spec from the Automation Lab.
  3. Rewrite the same spec using Selenium (Python) — get it green.
  4. Diff the two: which took more code? Which was harder to debug? Which failure output would you rather read at 4am?
  5. Point the Playwright suite at the buggy login and confirm the "expected behavior" assertions fail — that's a real regression suite catching real bugs.
