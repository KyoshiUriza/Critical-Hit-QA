Ten errors and their real fixes

Note the pattern: most of these are a locator problem wearing a timing costume. Diagnose the locator first.

#ErrorCauseFix
1 TimeoutError Element never became actionable within the timeout. Check the locator resolves at all before touching the timeout. Raising the timeout on a wrong locator just makes the failure slower.
2 strict mode violation Locator resolved to several elements. Scope to a stable ancestor or use filter(). Reaching for .first() re-introduces positional brittleness.
3 element is not visible Hidden, zero-size, or covered by an overlay. Wait for the state that reveals it. scrollIntoViewIfNeeded() only if genuinely off-screen. Never { force: true } as a first move.
4 element is not attached to the DOM Component re-rendered between locate and act. Use a Locator — it re-resolves on each action. Captured ElementHandles go stale.
5 Navigation timeout Waiting for a load state that never settles. Wait for a specific element or response. Avoid networkidle — polling apps never reach it.
6 Assertion failed Expected value doesn't match actual. Use auto-retrying web assertions (expect(locator).toHaveText()) rather than reading a value then asserting on the snapshot.
7 File upload failed Wrong path, or the input is hidden behind a styled label. setInputFiles() on the <input type="file"> itself; resolve paths from __dirname.
8 Popup / new tab not detected Listener attached after the action that opens it. Start waiting before clicking — Promise.all([page.waitForEvent('popup'), click]).
9 Flaky test Timing, shared state, or non-deterministic data. Diagnose, don't retry. Run it 100× locally to measure the rate, then fix the cause.
10 Browser closed unexpectedly Context or browser torn down while a test still runs. Let the test runner own the lifecycle. Don't call browser.close() inside a test that uses the page fixture.

CLI commands worth memorising

Commands are identical in JavaScript and TypeScript projects — only the spec files differ.

Running

npx playwright test                      # every spec
npx playwright test login.spec.js        # one file
npx playwright test --grep "checkout"    # by title pattern
npx playwright test --project=chromium   # one browser
npx playwright test --workers=1          # serial, for debugging
npx playwright test --repeat-each=100    # flake hunting

Debugging

npx playwright test --debug     # step through with the Inspector
npx playwright test --ui        # interactive UI mode (best default)
npx playwright test --headed    # watch it run in a real browser
npx playwright test --trace on  # capture a full trace every run

Code generation & reporting

npx playwright codegen example.com   # record actions into a spec
npx playwright show-report           # open the HTML report
npx playwright show-trace trace.zip  # inspect a captured trace

Setup

npm init playwright@latest        # scaffold a project
npx playwright install            # download browser binaries
npx playwright install --with-deps chromium   # CI-friendly, one browser
The three that earn their keep. --ui for authoring, --debug when one test misbehaves, and show-trace when CI fails and you can't reproduce locally. Trace viewer turns "no idea why it failed" into a DOM snapshot at the moment of failure.

A debugging order of operations

When a test fails and the reason isn't obvious, work in this order. It's roughly cheapest-to-most-expensive.

  1. Read the error, not the stack. Playwright's messages name the locator and what it resolved to. That's usually the whole answer.
  2. Does the locator resolve? await expect(locator).toHaveCount(1). If it's 0 or 3, stop — you have a locator bug, not a timing bug.
  3. Open the trace. show-trace gives you a DOM snapshot before and after every action, plus network and console.
  4. Re-run in UI mode. --ui lets you step and re-run a single test without restarting the suite.
  5. Measure the flake rate. --repeat-each=100 --workers=1. "Sometimes" is not a diagnosis; 7/100 is.
  6. Isolate state. Run the test alone. If it passes alone and fails in the suite, you have leakage between tests.

Steps 1 and 2 resolve the large majority. The instinct to jump straight to raising timeouts is what turns a ten-minute fix into an afternoon.
